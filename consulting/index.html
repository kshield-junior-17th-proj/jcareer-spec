문제 정의

이미지가 안전하면 단말도 안전할까

J사는 Windows 100대와 macOS 80대를 쓰는 가상 기업입니다. 이 숫자는 시나리오상의 자산 규모이지, 저장소에서 180대의 실물을 관찰했다는 뜻이 아닙니다.

보안 진단에서 자주 생기는 오해는 이미지와 실행 중인 단말을 같은 대상으로 보는 것입니다. 골든 이미지의 방화벽과 백신 설정이 올바르더라도 사용자가 로컬 관리자 권한을 얻었거나, 브라우저 세션이 남았거나, 배포 이후 정책이 바뀌었다면 실제 위험은 달라집니다. 반대로 현장 단말 한 대에서 이상이 없었다고 해서 이미지 공급망 전체가 검증된 것도 아닙니다.

이번 진단의 기준 질문

승인한 원본이 어떤 경로로 단말에 도착했고, 현재도 같은 통제를 유지하며, 검토가 끝난 뒤 민감한 흔적을 지웠다는 사실을 무엇으로 설명할 수 있는가.

먼저 밝히는 현재 상태

저장소에는 Windows 이미지와 3대 샘플 단말을 만들 수 있는 기본 비활성 정의가 있습니다. 실제 AMI 빌드, EC2 단말 배포, 원격 세션 관찰은 수행하지 않았습니다. macOS는 스크립트와 계약만 있고 MDM 또는 EC2 Mac 예외 경로가 결정되지 않았습니다.

Architecture

기준선과 현장 상태를 한 증거 사슬로 잇습니다

Windows와 macOS는 같은 점검표를 공유할 수 있지만 배포 수단은 같지 않습니다. Windows는 EC2 Image Builder로 검증용 AMI를 만들고 Systems Manager 터널을 통해 3대 샘플을 확인하는 경로를 준비했습니다. macOS는 물리 Mac과 MDM을 우선하며, EC2 Mac은 비용, 라이선스, 리전 용량을 승인한 경우에만 예외로 검토합니다.

검증 축을 두 개로 나눕니다

첫 번째 축은 이미지와 정책의 공급망입니다. 두 번째 축은 그 결과가 설치된 단말의 현재 상태입니다. 둘 중 하나만 확인하면 결론도 절반에 그칩니다.

Walkthrough A

Windows 골든 이미지부터 검토합니다

현재 소스는 Windows 11 단말이 아닙니다. Windows Server 2022 Desktop Experience를 업무 화면 검토용으로 구성하는 시뮬레이션입니다.

Image Builder 구성은 상위 이미지 버전을 고정하고, 암호화된 gp3 볼륨과 IMDSv2, Windows Firewall, Defender, Systems Manager Agent, 서명된 Edge를 검사하도록 작성돼 있습니다. RDP는 외부에 열지 않고 Systems Manager 터널의 loopback 연결로만 접근하는 설계입니다.

endpoint_image_contract.yaml정확한 상태 계약
platform: WINDOWS_SERVER_2022_DESKTOP_SIMULATION
image_strategy: AWS_EC2_IMAGE_BUILDER_AMI
current_execution_state: NOT_BUILT_OR_DEPLOYED
sample_profiles: [WIN-01, WIN-02, WIN-03]
access: SSM_TUNNELED_RDP_OR_FLEET_MANAGER
baked_secrets: PROHIBITED
  1. 01
    원본을 고정합니다.

    상위 이미지, 구성 번들, 파이프라인 설정을 버전과 SHA로 묶습니다.

  2. 02
    빌드와 시험을 분리합니다.

    이미지를 만든 사실과 Defender, Firewall, Edge 서명을 통과한 사실을 각각 기록합니다.

  3. 03
    승인 뒤에만 3대를 엽니다.

    WIN-01부터 WIN-03까지 정확히 세 대를 만들고 인바운드 규칙은 0개로 유지합니다.

  4. 04
    세션 종료를 검증합니다.

    최대 8시간 안에 종료하고 임시 Edge 프로필과 클립보드 토큰이 남지 않았는지 확인합니다.

확인한 것재현 가능한 소스와 차단 규칙

정의, 검증 스크립트, 승인 입력 계약이 저장소에 있습니다.

확인하지 않은 것AMI와 GUI의 실제 상태

빌드 ID, AMI ID, 세션 화면, 실행 로그는 아직 없습니다.

Walkthrough A, continued

macOS는 이미지를 만들기 전에 경로부터 결정합니다

macOS에는 준비, 설정, 검증, 제거 스크립트가 있습니다. 하지만 이 파일들은 서명된 설치 패키지나 MDM 프로필도 아니고, 이미지 배포 증거도 아닙니다. 물리 Mac 3대에 고객사 MDM 정책을 적용하는 경로가 우선안입니다.

권장 경로

물리 Mac + MDM

Apple 라이선스와 기존 업무 환경을 지키면서 FileVault, Gatekeeper, 방화벽, EDR, 브라우저 세션 정책을 검토합니다.

  • MAC-01 · 후보자 역할
  • MAC-02 · 채용 담당자 역할
  • MAC-03 · 관리자 역할
승인 필요 예외

EC2 Mac

전용 호스트 비용, 최소 할당 시간, 리전 용량, 원격 접속 방식까지 승인한 경우에만 검토합니다.

  • 베어 메탈 Dedicated Host
  • 호스트당 Mac 인스턴스 1대
  • 호스트 해제 전 최소 24시간
현재 결론

macOS AWS 리소스는 0개입니다. 물리 Mac과 MDM 사용 여부, Apple 정책, 담당자, 단말 접근 방식이 결정되기 전에는 배포 완료로 표시하지 않습니다.

Business boundary

Slack은 사라진 컴포넌트가 아니라 AWS 밖의 경계입니다

Windows와 macOS 소스에는 app.slack.com으로 가는 업무 바로가기와 세션 종료 보조 처리가 있습니다. 이것은 실제 Slack workspace, 계정 정책, 보존 규칙, AWS 알림 연동을 증명하지 않습니다.

업무 단말Windows 100 · macOS 80시나리오 자산
업무망 통제VPN + MFA · UTM시나리오 선언
외부 SaaSSlack운영 미확인

실제 진단에서는 SSO와 MFA 강제, 게스트와 외부 연결, 앱 설치 승인, 메시지와 파일 보존, 모바일 세션, 퇴사자 비활성화, 감사 로그 내보내기를 별도 확인합니다. 현재 저장소의 기본 비활성 webhook 소스는 이 운영 점검을 대신하지 못합니다. Amazon Q Developer, SNS, EventBridge 연동도 구현돼 있지 않습니다.

Publication rule

공개 AS-IS에는 사실만 남깁니다

외부에 공개할 문서라면 구현 사실과 다음 단계 제안을 한 문장 안에서 섞지 않아야 합니다. 특히 자산 수량과 실행 증거를 구분해야 합니다.

반드시 추가할 항목

  • Windows 100대, macOS 80대는 시나리오 자산 규모라는 설명
  • Windows Server 2022 Desktop Experience 시뮬레이션이라는 정확한 OS 표기
  • 이미지 정의, AMI 빌드, 단말 배포, GUI 관찰의 개별 상태
  • macOS의 물리 Mac + MDM 우선안과 EC2 Mac 예외 승인 조건
  • Slack은 AWS 밖의 운영 미확인 SaaS 경계라는 설명
  • 3+3 샘플은 검증 경로용이며 180대를 대표하지 않는다는 한계

추가하면 안 되는 항목

  • 실제 180대를 배포하거나 관찰했다는 표현
  • Windows 11 이미지, macOS 이미지, MDM 정책을 만들었다는 주장
  • Slack workspace와 AWS가 연동됐다는 주장
  • AWS 계정 ID, 자격증명, 내부 주소, 원본 state와 민감 로그
  • 실제 지원자 정보나 화면 캡처, 복구할 수 있는 개인정보
  • TRACE와 JC-RECEIPT를 단말 실행 인프라로 표현하는 도면

Operations note

실행 전 마지막 결정

다음 단계는 Terraform 적용이 아니라 사람의 범위 승인입니다. Windows 3대의 빌드와 세션 비용, macOS 물리 단말과 MDM 담당자, 자료 반입 금지, 세션 만료, 종료 후 삭제 기준을 먼저 정해야 합니다. GitHub CI는 정적 검사 경계이며 현재 이 단말 환경을 자동으로 AWS에 적용하지 않습니다.
